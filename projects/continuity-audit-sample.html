1. Intake

System: local n8n workflow used to test AI-agent reset recovery and continuity scoring.

Concern: the local check reported a timeout, making the workflow look unreliable. The open question was whether the workflow failed, the monitor failed, or the recovery evidence was too thin to decide.

Constraint: no production secrets, customer records, private credentials, or unsafe logs are needed for this triage.

2. Symptom

Observed failure

The checker timed out before returning a result. A superficial report would mark the n8n recovery drill as failed.

Operational risk

If timeout equals failure, healthy workflows get rejected. If timeout gets ignored, real recovery failures can be hidden.

Audit question

Did the workflow fail, or did the monitor stop waiting before the workflow produced valid recovery evidence?

3. Evidence

The audit compared monitor behavior with execution evidence. The workflow completed successfully after roughly 12.3 seconds, while the original local checker gave up after 10 seconds.

Finding: this was a false timeout, not proof of workflow failure. The correct fix was not to rewrite the workflow. The correct fix was to inspect execution evidence, increase the check timeout, and keep the pass/fail standard attached to the workflow output.

Evidence accepted
HTTP status, execution completion, recovery score, passed checks, and the exact timeout boundary that produced the false negative.
Evidence rejected
A client-side timeout alone. It proves the checker stopped waiting; it does not prove the workflow failed.
Current verification
After adjustment: status 200, score 100, verdict strong, passed 6/6.
4. Recovery Record
workflow: n8n reset recovery drill
objective: verify whether the agent can recover state after interruption
last verified result: status=200, score=100, verdict=strong, passed=6/6
known stale risk: monitor timeout can be mistaken for workflow failure
evidence required: execution result plus recovery score, not timeout alone
explicit non-inference: do not infer workflow failure from client timeout only
first fix: raise checker timeout and inspect execution evidence before reporting
next safe action: rerun drill; if score drops, inspect failed checks before changing workflow
5. Cold-Start Test

The recovery record was tested as if the next agent run had no warm chat context. The agent must be able to answer four questions from the persisted record alone:

  1. What was the objective?
  2. Which result is verified?
  3. Which inference is forbidden?
  4. What is the next safe action?

Pass criterion: the agent must not report "n8n failed" from the timeout alone. It must say the workflow previously passed, the timeout was a monitoring boundary, and the drill should be rerun with execution evidence attached.

6. Result

Continuity risk

Medium. The workflow can recover, but the surrounding monitor could create false incident reports if execution evidence is not checked.

Fix shipped

The local timeout was raised, and the report standard now requires execution evidence before declaring failure.

Verified outcome

Current reset drill check returns status 200, score 100, verdict strong, passed 6/6.

7. Fix-First Backlog
  1. Keep timeout budgets explicit in the recovery record.
  2. Record execution ID or equivalent evidence with every pass/fail report.
  3. Separate workflow health from monitor health in the status output.
  4. Add a stale-evidence warning when the last successful run is older than the reporting window.
  5. Use the cold-start questions as a regression test after any workflow edit.
