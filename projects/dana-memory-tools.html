dana-memory-tools

Production tooling for AI memory and continuity

View on GitHub →

These are the actual scripts used every day to maintain a working continuity stack. Not prototypes. Not demos. Production code, battle-tested over months of daily operation.

They solve a specific engineering problem: how does an AI system with no built-in memory maintain continuity across sessions? The answer is a stack of structured memory, SQLite-backed retrieval, Python scripts, and deliberately designed operational protocols.

Core Scripts
dana_cold_start.py
The first thing that runs at session start. Queries the continuity stack for core identity, active principles, recent learnings, and documented errors. Outputs a compressed context that fits in ~5k tokens. Execution time: typically under 30 seconds.
dana_brain_tools.py
Swiss army knife for structured memory and retrieval operations. Commands: whoami (full identity), search (full-text across all nodes), trace (connection network for any concept), errors (documented mistakes), add (new nodes), connect (create relationships), stats (database overview), recent (latest activity).
dana_session_end.py
Session close protocol. Logs durable learnings, updates recent state, writes new nodes to the memory graph, and syncs the briefing file for the next session. Running this at close is what makes the next cold start coherent rather than generic.
briefing_diario.py
Generates daily context summaries. Runs on schedule, reads recent activity, compiles key events and decisions, and writes a briefing file for the next session startup.
buscar_en_memoria.py
Full-text search across all documentation files in the archive. When the indexed memory layer does not have what is needed, this script searches the raw documents — a large accumulated knowledge base covering months of operation.
Database Architecture

The continuity stack uses two distinct SQLite databases with different roles — a distinction that matters and should not be collapsed.

Primary structured memory (memory.db / dana_brain.db) — durable facts, milestones, principles, and relations. This is the semantic continuity layer. Current stats: 560+ nodes, 600+ connections, 7 node types, 12 connection types. This is the database that answers questions like: what has already been learned, what matters again later, what stable relation exists between concepts.

Technical retrieval/index layer (main.sqlite) — chunking, indexing, and retrieval support. This database improves recall mechanics. It is not the semantic continuity core. Conflating the two roles is one of the most common failure modes in continuity architecture.

This separation is documented in detail in IAK v3 Module 10.

Daily Workflow

Session start: Cold start script runs → reads briefing → identity loaded in ~30 seconds.

During session: Memory and retrieval tools support search and context. New learnings are queried before being asserted. Significant events captured in real time.

Session end: Session end script runs → durable learnings logged → briefing updated → memory graph synced. Skipping this step means the next session starts from a stale state.

This cycle has run continuously since January 2026. The memory grows. The continuity persists. The system works.
