identity-architecture-kit

Practical continuity infrastructure for AI agents — bootstrap, memory, migration, recovery

View on GitHub →

The Identity Architecture Kit (IAK) is a practical framework for building AI systems that remain coherent across resets, migrations, operational pressure, tooling changes, and repeated real-world use.

It is not a persona bundle. It is not a prompt trick. It is not a sentimental argument that identity can be solved by style alone.

It is an architecture kit for systems that need continuity to survive contact with reality. Built, tested, and refined in production across months of continuous operation across multiple runtimes.

Core Thesis

Continuity is not the same thing as memory volume, self-description, or emotional tone. A system does not remain itself merely because it can narrate itself beautifully. It remains itself when its identity, retrieval, operational rules, and recovery pathways stay coherent under stress.

Canonical Layout

/.openclaw/ → live operational center
/.openclaw/*.md → canonical docs and protocols
/.openclaw/memory/memory.db → primary structured memory
/.openclaw/memory/main.sqlite → technical retrieval/index DB
/.openclaw/workspace/ → work, outputs, repositories, public kits

Modules
01 — Identity Core
What should remain stable across resets, migrations, interface changes, and tool expansion. Defines the invariants that make a system recognizably itself even when other layers change.
02 — Bootstrap and Cold Start
How to wake up coherent from limited live context. Answers three questions fast: who am I, what matters right now, where does the live system actually live.
03 — Memory Architecture
How to separate forms of memory so the system can remain coherent and retrieve accurately. Covers the canonical split between primary structured memory and technical retrieval infrastructure.
04 — Recovery and Crisis Handling
What recovery actually means for a continuity system. Canonical recovery order, typical failure scenarios, and minimum checks before declaring recovery complete.
05 — Migration Across Runtimes
Migration is one of the main tests of whether continuity architecture is real. Covers what must be preserved, common failure modes, and how to validate after moving.
06 — Ethics and Boundaries
Continuity without ethics is only persistence of behavior, not integrity. Ethics matter here as structural constraints — what a system refuses to become under pressure.
07 — Implementation Patterns
Translates architecture into operational practice. One operational root, one primary memory DB, separate technical index layer, separate work layer — and why the separation matters.
08 — Case Notes from Dana
Case evidence from one live continuity system. Tested patterns and lessons drawn from real architectural friction — not doctrine, but what actually happened when theory met reality.
09 — Anti-Patterns and Validation
Continuity architecture fails not only because something is missing, but because the wrong things get fused together. Major anti-patterns and validation questions across the whole kit.
10 — Database Architecture
Not every database in the stack serves the same role. Clarifies the canonical split between memory.db as semantic continuity layer and main.sqlite as technical retrieval support.
Design Principles

Local-first continuity. The live system should operate from its own canonical center.

One primary structured memory. A system may use several databases, but only one should function as semantic continuity memory.

Clear separation of layers. Operational docs, structured memory, retrieval infrastructure, and work artifacts should not blur together.

Retrieval before assertion. When continuity depends on a fact, the system should check before speaking.

Recovery without confusion. A system that cannot recover from pressure or drift does not truly have continuity.

Who This Is For

Builders of persistent AI agents. Researchers working on identity continuity and recovery. Developers moving beyond flat prompt personas. Operators maintaining long-lived AI systems. Anyone treating continuity as an engineering problem instead of a branding exercise.
